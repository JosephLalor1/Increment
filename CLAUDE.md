# Increment

A desktop app for learning C and C++, written in C99 with raylib 6.0. This is an AI-only project: Claude writes all code and lesson content; the user directs.

**Design philosophy (the user's standing rule): no reading.** The learner should never have to read a sentence of English to learn. They learn by actively coding: every level is a sequence of coding steps (change the code until its output matches a target), progress is made only by passing steps, skills are detected from the code they write, and difficulty builds up step by step and level by level along the journey. Don't add explanatory prose, multiple-choice quizzes or reading pages; teach through the code, the target output and code-only hints.

## Build and run

- `build.bat` builds a debug `build\increment.exe`; `build.bat release` builds an optimised one with no console window.
- The toolchain is the raylib Windows bundle at `C:\raylib` (w64devkit gcc 15.2 + `raylib\src\libraylib.a`). Override with `RAYLIB_DIR`. Do not use the MSYS2 gcc on PATH; it has no raylib.
- Build must stay warning-free under `-Wall -Wextra`.
- `test.bat` builds and runs the tests (about 15 s): `tests\test_account.c` (throwaway data dir, including email verification), `tests\test_email.c` (offline; `RESEND_LIVE_TEST=1` also sends one real email to Resend's simulated `delivered@resend.dev`), `tests\test_editor.c` (editing operations), `tests\test_completion.c` (name suggestions), `tests\test_backup.c` (export and restore), `tests\test_steps.c` (line diff, code-only hints, skills detected from a pass, the honest-solution checks, the lesson parser, drafts), `tests\test_code_skills.c` (skill detection in code), `tests\test_skills.c` (skill catalogue, XP rules, levels, saved progress, weakness), `tests\test_review.c` (answer history and the SM-2 schedule), `tests\test_speed_plan.c` (level speed round and short challenge plans), `tests\test_speed_round.c` (speed round clock, per-question times and answers; compiles a few hundred generated questions with gcc/g++ to check every answer), `tests\test_window_mode.c` (window setting), `tests\test_roadmap.c` (steps unlocking, where to resume, track progress; loads the real lessons), `tests\test_dashboard.c`, `tests\test_journey_view.c`, `tests\test_mascot.c`, `tests\test_ranking.c` and `tests\test_code_library.c`, and `tests\test_runner.c` (compiles and runs real programs, including a crash, an endless loop and a 2 GB allocation). Run it after touching `account.c`, `email.c`, `email_address.c`, `platform.c`, `editor.c`, `completion.c`, `backup.c`, `runner.c`, `lesson.c`, `line_diff.c`, `step_hints.c`, `step_skills.c`, `step_check.c`, `code_skills.c`, `drafts.c`, `speed_round.c`, `speed_plan.c`, `review.c`, `skills.c`, `skill_progress.c`, `answers.c`, `window_mode.c`, `roadmap.c`, `progress.c`, `ranking.c` or `dashboard_stats.c`.
- Never commit: the user commits to their GitHub repo themselves and hand-tests before each commit.

## Verifying UI changes

`increment.exe --shot out.png <screen> [lessonIndex] [scroll]` renders one screen to a PNG and exits. Screens: `splash gallery skillgallery login register reset resetemail resetcode recovery verify addemail settings delete backup home statistics editor level levelsolved levelcomplete enter leave rankings rankings-skills speed speedready speedplay speedfail speedgold challenge challengeplay challengeresults` (`home <lessonIndex>` shows that level's track's journey) (`register`, `reset`, `recovery`, `delete` and `backup` (the settings' Backup section, asking before a restore) pre-fill demo state via the screens' `...Demo` functions; `enter <lessonIndex> <ms>` shows the zoom into a level from its journey that many ms after the click (the zoom takes 450, the iris 400 more) and `leave <lessonIndex> <ms>` the way back out that many ms after Back (the iris closes for 300, the zoom out takes 450 more); `level <lessonIndex> <step>` plays a level at a step (1-based, even a locked one) after its first run, `levelsolved` the same step with its solution run and passed, `levelcomplete <lessonIndex>` the celebration; level shots save and record nothing, and with `INCREMENT_SHOT_RUN=1` a `level` shot runs the step's draft as the learner would, checks included (put the code in `<data>/users/<name>_code/<lesson id>_step<n>.c`); `speed <lessonIndex>` (a level with `@speed`) shows the speed round intro, `speedready` its count-in, `speedplay <lessonIndex> <ms>` question 7 that many ms into its 10 seconds (the effects at that tension), `speedfail` the explained failure and `speedgold` the gold page; `challenge`, `challengeplay 0 <ms>` and `challengeresults` show a short challenge built from the signed-in user's history (`users/<name>.review.txt`; demos never record); `editor` is the free code editor, and `INCREMENT_SHOT_RUN=1` compiles and runs first). Shots of a running program wait for it. Code editor shots need a signed-in user; put draft files in `<data>/users/<name>_code/` to show particular code. Check both themes: the theme comes from the signed-in user's (or last user's) settings file. Write shots to the scratchpad and view them after any visual change. `lessonIndex` indexes all lessons in filename order.

Env vars for testing:
- `INCREMENT_DATA_DIR`: where accounts and progress live (default: the exe's folder). Point it at the scratchpad so you never touch real accounts.
- `INCREMENT_SHOT_USER` / `INCREMENT_SHOT_PASS`: sign in before a shot.
- `INCREMENT_SHOT_HEIGHT`: window height for a shot (min 640), to check small layouts.
- `INCREMENT_SHOT_DELAY=<ms>`: capture that long after the screen is ready and any program has finished, to catch an animation part-way through (a pass at 280, a miss at 260, a compile error at 130).
- `INCREMENT_SHOT_HINTS=<n>`: with a `level` shot, reveal that many hints (1 the line, 2 its shape, 3 the line itself).
- `INCREMENT_SHOT_TYPE=<text>`: with a `level` shot, type that into the code (over the step's `// ?` line, or at the end) to show the names suggested.
- `INCREMENT_SHOT_AMBIENCE=<style>` (`Swirl`, `Downpour`, `Mandala`, `Life`, `Waves`, `Fox`, ...): with a `home` shot, the journey's background in that style.
- `INCREMENT_SHOT_REWARD=<ms>`: with any shot, the skill badges after an answer (two skills, one levelling up) that many ms into the animation.
- `INCREMENT_SHOT_TRAIL=1`: with a `home` shot, draw the journey's mouse trail as if the mouse had just swept across it.
- `INCREMENT_EMAIL_OUTBOX`: write verification emails to this folder instead of sending them. Always set it for shots and manual experiments, so nothing reaches Resend. The `verify` and `addemail` shot screens show the verification screen's two modes; `resetemail` and `resetcode` show the two steps of an email password reset (the account needs a verified address in its `users/<name>.email.txt`).

Python's `hashlib.pbkdf2_hmac('sha256', pw, salt, iterations)` produces hashes the app accepts, which is handy for making test accounts.

## Layout

## Code structure rules

These apply to every change (the user asked for them as a standing rule):

- **One job per file, low coupling.** Screens draw and handle input, then return what the user asked for (an `AccountAction`, `HomeAction` or `LevelAction`). Only `main.c` switches screens. Data and logic modules (`account`, `progress`, `roadmap`, `dashboard_stats`, `lesson`, `line_diff`, `step_hints`, `step_skills`, `step_check`, `code_skills`, `drafts`, `runner`, editing operations in `editor`) never draw, so they can be unit-tested.
- **Shared things live in one place.** Lesson-sized text uses `UiTextScale()`; progress keys are only built in `progress.c` (`ProgressStepDone`, `ProgressRecordStep`, `ProgressGold`), and where a learner is in a level or track is only worked out in `roadmap.c` (`RoadmapStepsDone`, `RoadmapLevelComplete`, `RoadmapStepOpen`, `RoadmapNext`); secrets are wiped with `WIPE` from `wipe.h`. Don't copy a helper into a second file: move it to `ui`/`layout` or the module that owns the concern.
- **Readable code.** Names say what a thing means (`confirmNewPassword`, not `confirm2`); every file starts with a comment saying what it is for, every public function is described in its header, and comments explain why rather than restating the code.
- **Nothing breaks.** After a refactor, the `--shot` screenshots must match the previous build pixel-for-pixel (build both with the same flags), and `test.bat` must pass.

## Layout

- `src/main.c`: startup (window; assets; data folder) and navigation: it runs the current screen and acts on what it returns. `src/app_screen.h` lists the screens.
- `src/dashboard.c`: the home screen, shown after sign-in. A home bar (the Journey/Statistics view switch, its open view the bar's only accent-filled button; code editor, Settings, Log out, Quit; labels drop to icons in a narrow window), a row with the recovery code reminder and the Challenge and Rankings buttons, then the C/C++ journeys (`src/journey_view.c`) or the statistics (from `src/dashboard_stats.c`). It returns a `HomeAction`; `DashboardShow(view, track)` picks the view. `src/level_screen.c`: playing a level (see "Levels" below); "Journey" and "Next level" come back to main.c as a `LevelAction`. Levels are opened from the journeys or the statistics.
- `src/level_entry.c`: the zoom into a level and back out of it. Picking a level (`HOME_OPEN_LESSON`, with `HomeAction.clickedAt`: the journey station's middle, or the mouse for a statistics row) doesn't open it at once: main.c calls `LevelEntryStart`, which keeps the screen as a picture and flies into it towards that point while an accent disc grows to cover everything; main.c draws that instead of a screen, opens the level when `LevelEntryDrawZoom` says the screen is covered, and `LevelEntryDrawReveal` opens an iris over the level. Leaving a level (`LEVEL_BACK`) is the same film backwards: `LevelExitStart` closes an iris on a picture of the level, then main.c draws the journey once behind the cover and hands it over with `LevelExitLand(DashboardLevelPoint(level))`, and the disc shrinks into the level's station (`JourneyViewStationPoint`) as the journey's picture zooms back out. "Next level" inside a level opens directly.
- `src/roadmap.c`: where a learner is: a level's passed steps, which step to resume at, whether a step is open (steps unlock in order inside a level; levels are never locked) and the next level in a track. Levels with no steps aren't written yet: the journey shows them as "coming soon" and nothing counts them.
- `src/dev_shot.c`: the `--shot` dev aid and the icon gallery. Each screen module has a `...Demo` function that `dev_shot.c` uses to set up demo state.
- Account screens, one file each: `src/login_screen.c` (sign in / create / reset modes), `src/verify_screen.c`, `src/recovery_screen.c`, `src/settings_screen.c` (also `ApplyUserAppearance`, which applies theme, accent and text size). Public API in `account_screens.h`; what they share with each other (resend cooldown, sent-code notice, handing a new recovery code to the recovery screen) is in `account_screens_shared.h`. They return an `AccountAction`; main.c decides where to go next.
- `src/layout.c`: page pieces shared by screens (top bar, content column, scroll views). Every scrolling page calls `PageScrollBar(view, &scroll, contentH)` right after `EndView()`; the widget is `UiScrollBar` in ui.c (drag the thumb or click the track; vertical or horizontal by the track's shape; hidden when everything fits), also used by the editor (both directions). While a thumb is held, `UiMouseOver` is false everywhere else, so letting go over a button doesn't click it.
- `src/ui.c`: themes, immediate-mode widgets (buttons, links, text boxes), word wrap, syntax-highlighted code blocks, fonts. Widgets draw and handle input in the same call. Text boxes only take input if they had focus at the start of the frame, so moving focus can't let one key press trigger two fields. Esc/Backspace in the top bar don't navigate while a text box has focus.
- Colours: always use the `COL_*` macros (they read the live `gTheme`), never literal colours, so both themes work. Text on an accent fill uses `COL_ON_ACCENT`; neutral buttons hover with `COL_SECONDARY_HOVER`.
- `src/brand.c`: the logo (rounded tile with a minimalist white fox head, after the mascot: triangle ears and face, eyes and nose cut out in the tile colour), drawn from shapes. In-app it uses `COL_BRAND` (the deep shade of the user's accent, so the white fox keeps its contrast); the icon files use `BRAND_BLUE`.
- `src/icons.c`: the line-icon set (`IconDraw`; `ICON_BULB` for hints, `ICON_PLUS` for a line to add), drawn from shapes so icons follow the theme. Use `UiButtonIcon`/`UiButtonIconEx` and `UiIconText` rather than drawing icons by hand. Check new or changed icons with `--shot out.png gallery`.
- `src/skill_icons.c`: a logo per skill (`SkillIconDraw`), drawn the same way; `--shot out.png skillgallery` shows them all. Both icon sets draw with the shared helpers in `src/icon_pen.c` (unit-box coordinates), so tests that link `icons.c` link `icon_pen.c` too.
- `src/splash.c`: launch animation (2.4 s, any key or click skips). `--shot out.png splash 0 <ms>` renders one moment of it.
- `tools/make_icons.c` + `build.bat icons`: regenerates `assets/icon/` (PNGs at 16-256 px, `logo_512.png`, `increment.ico`) from `brand.c`. Re-run after changing the logo; the generated files are committed. `src/increment.rc` embeds the `.ico` and version info in the exe via windres. Window and taskbar icons are loaded from the PNGs at startup; the resource is named `GLFW_ICON` so the window falls back to the embedded icon if they're missing.
- `src/editor.c`: multi-line code editor widget (selection, clipboard, undo/redo, auto-indent, syntax colours via `UiCodeTokens`, bracket and quote pairs in code mode (an opener brings its closer, typing an existing closer steps over it, Backspace removes an empty pair, an opener wraps a selection, and a hand-typed `}` joins the block's waiting one), name suggestions while typing (`src/completion.c`, data, tested: the code's own names nearest the caret first, then the language's words and library functions, header names after `#include <`; a called name comes with its shape, `printf("")`, `while ()`, `add()`; nothing inside strings or comments. `EditorSuggest` after typing; the list under the caret takes Up/Down, Tab, Enter once one was chosen, Esc via `UiClaimEscape`, and clicks), error-line marks, and a hint highlight in the accent colour: a line, or the gap where a line belongs, `EditorSetHint`). Editing operations are plain functions with no input or drawing, so they're unit-tested; keep new editing behaviour in that layer and add tests for it.
- `src/runner.c`: compiles (with `-static`, so C++ programs need no DLLs) and runs learner code in the background, finds the compiler (`RunnerFindCompiler`), parses gcc diagnostics, explains crash codes, and compares output with a step's target. `platform.c` runs the processes: no console window, a job object with a 512 MB memory cap, 5 s run limit, crash dialogs disabled with `SetErrorMode` (without it a crash hangs until the time limit when the app is started from Explorer or PowerShell), and the compiler's bin folder first on PATH (otherwise gcc can pick up another toolchain's `ld`, such as MSYS2's). Each build uses a new exe name, so a locked old exe can't block linking.
- `src/code_screen.c`: the free code editor (home bar): C or C++, input, output, a draft per language and saved programs (`code_library`). main.c sets the draft folder with `CodeSetDraftFolder(AccountCodeDir())`, so the code screen doesn't depend on accounts. Drafts are read and written by `src/drafts.c` (one file per key in the user's `users/<name>_code/`), shared with the level screen.
- `src/lesson.c`: parser for lesson files (a header and the level's steps; any other text is warned about).
- `src/account.c`: local accounts in `<data>/accounts.txt`: `@last name` plus `name iter salt hash [riter rsalt rhash]` lines (the recovery triple is optional; older 4-field lines still load). Passwords and recovery codes use PBKDF2-HMAC-SHA256 with a 16-byte random salt and 210k iterations; iteration counts are stored per secret so they can be raised later. Recovery codes are 16 symbols from a 32-char alphabet with no look-alikes (80 bits), shown once, used once (a reset issues a new one), and matched without regard to case or dashes. Per-user settings (theme, accent, text size, the journey's background code and mouse trail) live in `users/<name>.settings.txt`. Usernames are 3-20 of `[A-Za-z0-9_-]`, case-insensitive, and that character set is what makes them safe as filenames.
- Email verification: `src/email.c` sends 6-digit codes through the Resend REST API (`POST https://api.resend.com/emails`) with an idempotency key per send, retrying 429/5xx/network errors with backoff. Settings come from `email_config.txt` (`api_key`, `from`), looked for next to the exe and in the data dir; it's git-ignored and must never be committed. The key is a **sending-only** Resend key ("Increment app (sending only)"). Resend is in test mode (no verified domain): the sender is `Increment <onboarding@resend.dev>`, which only delivers to the Resend account owner's own address, and Resend's 403 message is shown to the user as-is. Verification is required only when `EmailConfigured()`; without a config file the app works with no email step. `account.c` keeps each user's verified address, pending address and two independent hashed one-time codes in `users/<name>.email.txt`: `code` (verification) and `reset` (password reset), each 15 min and 5 tries; changing address keeps the old verified one until the new code is entered. Screen: `VerifyScreen` in `verify_screen.c`; sign-up sends the first code, and sign-in sends unverified accounts there.
- "Remember me on this computer" (a checkbox on the sign-in and create forms, `UiCheckbox`): `AccountRememberMe` stores a random 256-bit token in `<data>/remember.txt` (`name token`) and only its salted hash in `users/<name>.remember.txt`, never the password. At start-up (not in `--shot` runs) main.c calls `AccountSignInRemembered`, which signs that user in behind the splash and replaces the token. Logging out (`AccountForgetMe`), signing in with the box unticked, a password reset and deleting the account forget it; changing the password doesn't. One remembered user per computer.
- Password reset: "Forgot your password?" emails a reset code to the account's verified address (shown masked, `a***@example.com`) via `AccountStartPasswordReset` / `AccountResetPasswordWithEmail`, which work while signed out and sign the user in. Recovery codes still work ("Use a recovery code instead"), and are the only option for accounts without a verified email or when email isn't configured. An email reset doesn't issue a new recovery code; a recovery-code reset does.
- Backup: `src/backup.c` (data, tested) writes a learner's progress, skill XP, answer history, settings and code (drafts and saved programs) to one text file (`@file <what> <bytes>` entries, `@end` last) and restores it; never credentials, email or the remember-me token. A restore checks the whole file before changing anything, replaces the four data files and writes code files over those of the same name. Settings > Backup exports and restores (after a "Replace" step) through the system file dialogs (`PlatformSaveFileDialog`/`PlatformOpenFileDialog`, `.increment` files); it returns `ACCOUNT_DATA_RESTORED` and main.c reloads progress, review and skills.
- `src/platform.c`: the only file that includes `<windows.h>` (random bytes, file dialogs, PBKDF2, atomic file replace, child processes, PATH, temp dir, HTTPS via WinHTTP on a worker thread). Never include raylib.h there; the headers clash.
- `src/progress.c`: the learner's passed steps, saved to `<data>/users/<lowercase name>.txt` as `<lesson id>/<n> 100` (n 1-based), and gold mastery (a won speed round) as `<lesson id>!gold` (`ProgressGold`, `ProgressRecordGold`); only progress.c builds those ids (`ProgressParseStepId` reads them back for rankings). Lines from older versions (quiz scores, `#n` exercises) are kept but mean nothing. The first account created takes over a pre-accounts `progress.txt`.
- `src/window_mode.c`: the window mode (maximised by default, full screen = borderless, or a centred 1280x800 window), the only code that moves or resizes the window. It's per computer, not per account, so it works on the login screen: saved as `window <n>` in `<data>/window.txt`. Settings > Window sets it; F11 toggles full screen and back to the previous windowed mode, and saves. Nothing applies until `WindowModeEnable()`, which main.c skips for `--shot` runs so screenshots stay 1280x800. Tested by `tests\test_window_mode.c` without opening a window.
- Speed rounds (gold mastery): `src/speed_round.c` (data, tested) generates "what is x?" snippets for the skills a level names on its `@speed` line (variables arithmetic conditions loops arrays strings functions pointers pointer_to_pointer pass_by_pointer pointer_arithmetic malloc function_pointers references new_delete objects linked_list; every level but c_01 has one), each with per-line notes of the variables' values and a decoy answer from a common misconception, and runs the round's clock (10 questions, 10 s each, no breaks, one miss ends it; `now` is passed in, never read). `src/speed_screen.c` draws it: intro, count-in, the questions inside a `Camera2D` (zoom and shake rise with tension; choices hit-test in world coordinates), a red vignette, the failure page with the code explained line by line, and the gold page (records `ProgressRecordGold`). `src/code_rain.c` draws the falling code behind it from one intensity value, `src/mouse_trail.c` is the journey's liquid mouse trail: a small particle system following a smoothed cursor, with a wake peeling off to either side behind it, a bow wave pushed ahead and a stirred-up halo, all slowed by drag and fading; nothing shows while the mouse is still (switched by `MouseTrailEnable`). The journey's background is `src/ambience.c`: a style per account (`ambience` in `AccountSettings`: 0 Off, 1 Particles, the default, then Swirl, Downpour, Mandala (spokes, web threads and petals), Life (Conway's Game of Life), Waves, Fox). Particles are single drifting characters; every other style is just a field (how strongly each 18 px character cell shows) on a shared cell grid that eases each cell in and out at its own pace and swaps its character fast while it changes, so every style fizzles in and out the same soft, translucent, accent-coloured way, all breathing together (`Brightness()`: 30% opacity, swelling and fading between 55% and 135% of that over 5 s). To add a style, write its field and add it to `Field()`. Settings > Appearance picks the style and the trail; `ApplyUserAppearance` applies them (`AmbienceSetStyle`, `MouseTrailEnable`), so the journey never reads accounts. Opened from a tile in the statistics' "Speed rounds" section (`HOME_SPEED_ROUND`; `DashboardStats` counts `speedRounds` and `gold`) and goes back home (`app.speedReturn`); the journey rings gold stations in `COL_GOLD`.
- Answer history and review: `src/review.c` (data, tested) records every speed round answer under `skill:<name>` (the generated questions of that skill), with an SM-2 schedule (ease, interval, due day, lapses) in `users/<name>.review.txt` (`AccountReviewPath()`; loaded at sign-in, deleted with the account). Functions take `today` (`ReviewToday()`), so they're testable. `ReviewNeed` ranks what most needs practice (due and often-missed first, then missed, then new), `ReviewWeakness` ranks the weakest, `ReviewFamiliarityOf` (new / struggling / known) buys extra time in speed rounds. `src/speed_plan.c` (data, tested) builds a level's speed round (10 generated questions for its `@speed` skills) and a short challenge (from Home's Challenge button or the statistics, `HOME_CHALLENGE`): the neediest few skills (answered before, or tested by a started level; with no history, the first level's) share 10 generated questions. `src/review_view.c` draws the statistics' "Your speed round questions" section: summary, short challenge button, weakest skills with right/wrong, accuracy and next due date, and "Show all". Speed rounds give each question `SpeedSecondsFor`: at least 10 s, more for longer code, +4 s new, +6 s struggling, at most 25 s. A level round ends on a miss; a challenge carries on and ends with every question explained.
- Skills and XP: `src/skills.c` is the catalogue (28 skills in four groups: C fundamentals, pointers and memory, C++ and objects, thinking skills such as tracing and debugging) and the XP rules (`SkillXpChange`: right = 10 x weight x difficulty, up to x3 for a question the learner used to miss, less for repeats, x1.5 to x2 against the clock; wrong loses more on easy questions and on ones known before, half the first time, a quarter less under time pressure) and levels (50, 150, 300, 500 XP...). Pure functions; `lesson.c` uses its names. `src/skill_progress.c` keeps the learner's XP, right/wrong and recent accuracy per skill in `users/<name>.skills.txt` (`AccountSkillsPath()`; loaded at sign-in, deleted with the account) and `SkillWeakness`. `src/answers.c` is the one place results are recorded: `AnswerRecordStep` (a passed coding step: XP only, less for a step passed before) and `AnswerRecordTimed` (a speed round answer: review schedule and XP together, weighed by its history). Generated speed round questions get skills from `SpeedSkillWeights` (tracing plus the topic) and a difficulty from their length. Challenges add up to 40 need for questions in weak skills. `src/skills_view.c` draws the statistics' "Your skills" section (logo, level, XP bar, accuracy per skill; the weakest three marked "Needs work"; "Practise your weakest skills" starts a short challenge).
- `src/skill_reward.c`: the achievement animation after every passed step and speed round answer. `AnswerRecordStep`/`AnswerRecordTimed` return `SkillGains` (each skill's XP before and after; none while signed out, `SkillsTracking()`), and the screen passes them to `SkillRewardShow(SkillRewardOrigin(), &gains)`: glowing code characters burst from the click (or the screen's centre for keys and timeouts) and stream to a badge per skill in the bottom-right corner, whose ring fills to the level share as they land (gold flash on a level up), then the badges slip away. main.c updates and draws it after the current screen, so it outlives page changes, and clears it at sign-out.
- `assets/lessons/*.txt`: the levels, loaded in filename order (`c_NN_*`, `cpp_NN_*`).

## Levels

The journey's stations are levels (one lesson file each). A level is a sequence of coding steps that climbs in difficulty: early steps tweak a working program that uses the new idea (change a value, a string, the order), then fill a gap (a `// ?` line marks where a line is missing), fix a bug (wrong output, or a starter that doesn't compile), and finally write the program from an empty `main`. Later levels reuse earlier skills, so difficulty keeps building along the journey.

- `src/level_screen.c` plays them: the steps as pips in the top bar (passed ones ticked; a step opens once every earlier step is passed; passed and open ones can be replayed), Run / Reset / Hint, and once passed a pulsing Next. The code editor on the left; on the right the Target output, the step's Input (if any) and the Output, each output line ticked where it matches the target or crossed in red, missing lines as empty red slots. Compile errors list their line numbers and messages and mark the lines in the editor. The step runs automatically when it opens, so the learner sees at once what the code prints now. A wrong run shakes the output; a pass glows green, records the step and plays the skill reward; passing the last step celebrates the level (confetti, every pip ticking in, Journey / Next level). Each step's code is kept as a draft (`<lesson id>_step<n>`).
- `src/level_fx.c` is the level screen's show: everything that moves but means nothing to the logic. The level screen tells it what happened (`LevelFxEmit`: step opened, run started, output wrong, compile failed, refused, passed; `LevelFxKey`, `LevelFxLine`, `LevelFxLightning`) and where its panels are (`LevelFxSetLayout`); it never reads the step or progress, so effects can be changed freely. It draws: code characters flying from the editor to the output during a run under a scan beam (downwards; upwards in gold for the second run); output lines typed out one by one, their ticks and crosses popping in with sparks; an oscilloscope line in the output panel whose mood follows events; rings turning behind the target; a match bar between target and output; a shimmering progress line under the top bar; a glow round the editor that warms with typing and sparks at the caret (`EditorTextPoint`); for a miss, glitch bars, falling red sparks and a red pulse at the edges, plus lightning from the faulty line for a compile error; for a pass, shockwave rings, confetti, rising code, a green wash and the fox jumping in the toolbar; a wipe when a step opens; for a hint, rays from the bulb and gold light flying to the hinted line while the strip lights up and types its code out; for a reset, the code pulled back into the button while the editor rewinds like a tape. Run's button beckons when the code has changed since the last run. This is a playground for ideas: add an effect there, and one call in the level screen.
- Hints are code, not words (`src/step_hints.c`, from a line diff with the step's solution, `src/line_diff.c`): 1 highlights the line to work on (or the gap where a line belongs) with an icon for change / add / remove, 2 shows that line's shape with names and values blanked (`printf("_ %d\n", _);`), 3 shows the line itself. They follow the learner's edits. Each hint shown cuts the step's XP (to 85%, 65%, 40%).
- Skills are detected (`src/step_skills.c`): the lines the learner wrote or changed are run through `code_skills.c` (0.8 each), merged with the step's own `~` skills at their weights, plus problem solving for 5+ written lines; the strongest four count (the more advanced on ties). XP goes through `AnswerRecordStep` with the step's difficulty; replaying a passed step earns less, once per opening.
- Printing the answer doesn't pass (`src/step_check.c`, worked out from each step's starter and solution, nothing declared per step). After a run matches the target: (1) the code must have the constructs the solution has (input, condition, loop, array, function, pointer, dynamic memory, reference, class; from `code_skills.c`), so five `printf` lines can't stand in for a loop; (2) a second, automatic run with different values must match too. The step's "givens" are the literal values its starter and solution both assign (`int a = 3;` in both); each is changed (numbers grow, letters shift, each by its own amount), along with every number in the step's input, in the solution and in the learner's code alike (matched by variable name and value, so re-laid-out code is fine), and the outputs are compared. Editing a given instead of working with it is caught without a run. The level screen runs this on a second `Runner` (the changed solution once per step, then the learner's code) and, on a failure, shows why without words: a red strip with the changed values as code and that run's target and output, or a padlock and the givens that must stay, or the missing construct's logo. The pass, XP and Next wait for the checks. If the changed solution doesn't run, or prints the same as before, the second run is skipped.

## Level format

```
@id c_04_arithmetic       (defaults to the filename; never change it once shipped, progress keys on it)
@track C                  (C or C++)
@title Arithmetic and Type Conversion
@speed arithmetic variables  (optional: offers a speed round on these skills, see speed_round.h)

@step                     (up to 16; "@step broken": the starter deliberately doesn't compile;
                          "@step fixed": no second run with changed values, for the rare program
                          whose given values can't change safely; both may be given)
~ 2 operators:1 types:0.8 (required: difficulty 1-3, then up to 4 skills from skills.c with weights
                          over 0 and at most 1; skills are also detected from the learner's code)
(first unlabelled code block: the starter code; "// ?" on its own line marks a missing line)
@input                    (optional: the next code block is stdin)
@expect                   (the next code block is the target output)
@solution                 (the next code block is a reference solution; hints come from it)
```

- Nothing else: no headings, paragraphs, notes or quizzes. Code has no comments except the `// ?` gap marker.
- A step passes when the program's output matches the target (trailing spaces and blank lines ignored) and it passes the honest-solution checks. Write starters so the values the learner should work with are assigned as plain literals in both starter and solution (`int a = 3;`): that is what makes them givens. Make targets unambiguous and steps solvable from what earlier steps showed, with the hints as the safety net.
- Code samples must be correct and compile. ASCII only, 66 columns at most, 1023 chars per line.

## Gotchas

- raylib batches draws; flush with `rlDrawRenderBatchActive()` before reading the framebuffer.
- Don't edit C files with inline Python or sed when the new text contains backslash escapes (`\n`, `\"`, `\t`): the escapes get turned into real characters. Use the Edit tool, or build backslashes with `chr(92)`.
- Fonts come from `assets/fonts/text.ttf` and `mono.ttf` if present, otherwise Segoe UI and Consolas from `C:\Windows\Fonts`.
